identifies Beta 3 as testing-only, not for production. The
[PGDG 19 component](https://apt.postgresql.org/pub/repos/apt/dists/noble-pgdg/19/)
is explicitly provisioned. Both installed server and dev packages must match
`19~beta3-*`; candidate resolution also rejects changed/missing betas before
installation. No fallback to GA, another beta, a skip, or conditional success
is allowed. Docker separates `PG_MAJOR=19` from `PG_IMAGE_TAG=19beta3`.
The required image check pins the official multi-architecture index digest
`sha256:f0056b553c58e4533ba81921d9bd5b49641d4fa176e1add956a678b034007ac4`;
tag disappearance or movement fails closed. Provider packages are deliberately
disabled for the beta image; core extension/roles/policy/backup/restore remain
required. Stable PG17/18 provider requirements remain unchanged.

GA promotion is an explicit reviewed transition: demonstrate official GA
server/dev packages and base images, update provisioning and image identity,
change the pinned stable matrices and their mutation guards, replace beta
compatibility deliberately, and update support documentation. A feature named
`pg19` alone does not establish GA support.

## Homebrew source mechanics and compatibility

The formula itself supplies pgrx's Darwin `dynamic_lookup` linkage and sets
`MACOSX_DEPLOYMENT_TARGET` to Homebrew's `MacOS.version`, using Homebrew's selected
SDK. This follows Homebrew's host source-build policy, not Rust's older default
minimum or a hard-coded OS release. A binary built on a newer macOS is not
promised to run on older macOS; build on the intended host. Existing Rust flags
are appended to, including Cargo's encoded-flags precedence; Homebrew's separate
Rust flags remain intact. The installed library uses PostgreSQL 16+ Darwin
`.dylib` naming (Linux retains `.so`). Both Cargo and pgrx homes are isolated in the build.

Before tagging, run `scripts/test-homebrew-packaging.py NEW_EVIDENCE_DIRECTORY`
on arm64 macOS from a clean committed checkout. It audits the unchanged real
formula strictly, then installs and tests a separate local probe using a
SHA256-authenticated immutable Git archive of that commit. The probe changes
only its class/name, source URL/digest and version assertions. Its install runs
the formula's direct `cargo-pgrx pgrx package`, without ambient linkage or
deployment overrides. The portable structural/mutation gate is
`tests/test_homebrew_packaging.py`; it is not a substitute for this live gate.
The actual GitHub archive URL/digest, final source installation and `brew test`
remain mandatory post-tag gates. Synthetic source success does not pass them.

## Permanent historical cleanup evidence limitation

A final search of retained recovery/review evidence and available Docker
container/volume metadata and retained events did not recover ownership proof
for these two earlier deleted volumes:

- `62dc0a2e7b6546bf60c1bb785b397efdeea93e578b18499d0c726aae1331d02b`
- `d1ed4fbdc87c1d2a79c75cc213e94efecb4fb332c8e6c5f149232974a0d772bd`

Eight of the ten explicit volume deletions have retained ownership proof. These
two have only successful deletion receipts. The historical claim “only owned
resources were cleaned” therefore **cannot be established for those two**.
There is no evidence unrelated data was deleted. Absence of surviving metadata
is not ownership proof; retain this limitation permanently, including in future
handoffs, rather than upgrading the historical claim after newer tests pass.

Future test cleanup uses `scripts/create-owned-container.py` and
`scripts/cleanup-owned-container.py`. The creator explicitly allocates random
named volumes for image-declared mountpoints, with a separate creation nonce and
run label, then exclusively publishes fsynced volume and exact container creation
receipts. Smoke probe, main database and restore containers all use this path.
Cleanup never uses `docker rm -v`. Without a creation receipt, all volumes are
preserved, including borrowed anonymous volumes, even after container removal.
With a receipt, exact container creation metadata and volume labels/creation
metadata must match, including repeated inspection after receipt publication.
Deletion uses explicit non-force volume removal; in-use volumes remain protected.
Inspect or receipt failures preserve resources for inspection. Interrupted creates
can leave labelled resources; do not guess ownership to remove them automatically.

Receipts require a private, trusted per-run directory and exclusive orchestration
of the resources they identify. Docker's volume API has no immutable volume ID or
conditional compare-and-delete operation: it cannot defend a volume-name deletion
against a concurrent privileged daemon client replacing that name between inspect
and removal. Such clients must not share ownership of a cleanup run. Observed
identity changes fail closed; there is no claim of transactional Docker deletion.
Never use a global prune or infer ownership from association or a name prefix.

# Code Catalogue System Specification

**Status:** Revised implementation specification  
**Version:** 1.1.0  
**Last updated:** 2026-08-30 (adversarial-review remediation)  
**Primary storage:** PostgreSQL 16+  
**API style:** JSON REST over HTTPS

## 1. Overview and goals

### 1.1 Purpose

Code Catalogue is a multi-tenant service for storing, discovering, versioning, generating, and distributing reusable code. A catalogue entry may be a single snippet, a multi-file example, or a parameterized scaffold. Every content edit creates an immutable version. Entries can be public, private to an owner, or shared with teams.

The system exposes a REST API for the web UI, CLI, automation, and synchronization between independent instances. PostgreSQL is the system of record. Object storage is optional for large export archives; source files and normal-sized release bundles remain representable in PostgreSQL.

### 1.2 Goals

1. Store snippets, examples, and scaffolds in multiple programming languages.
2. Retain immutable, addressable versions and a complete audit trail.
3. Associate entries with normalized tags and hierarchical categories.
4. provide syntax-highlighting metadata without binding clients to one renderer.
5. Provide deterministic scaffold rendering with typed variables and safe conditionals.
6. Search by text, tag, language, kind, ownership, visibility, and update time.
7. Export/import catalogues as canonical JSON or ZIP bundles.
8. Synchronize changes and deletions incrementally between trusted instances.
9. Enforce public, private, owner, and team access consistently across API and search.
10. Support scoped, revocable API tokens without storing plaintext credentials.
11. Run as a stateless HTTP service backed by PostgreSQL, with rolling upgrades.

### 1.3 Non-goals for version 1

- General-purpose Git hosting, branching, merging, or pull requests.
- Executing arbitrary uploaded code on the API nodes.
- Resolving third-party package dependencies.
- Real-time collaborative editing.
- A Turing-complete template language or arbitrary template-side functions.
- Bidirectional identity federation between instances. Synced content retains source provenance but is governed locally after import unless configured as a mirror.

### 1.4 Core concepts

- **Entry:** Stable identity and mutable metadata for a catalogue item.
- **Version:** Immutable snapshot of entry content and version-specific metadata.
- **File:** Named content unit within a version. Single-file snippets still use one file.
- **Release:** Named, immutable pointer to a version, usually a semantic version.
- **Scaffold:** Entry whose files may contain template directives and whose version has a variable schema.
- **Origin:** Instance and remote identity from which an entry was imported or synchronized.
- **Change:** Monotonic event used for audit and incremental synchronization.

### 1.5 Required invariants

- Entry IDs and version IDs are UUIDs generated by the server using UUIDv7 where available.
- `(entry_id, version_number)` is unique and version numbers increase by one under a row lock.
- Version rows and version files are immutable after commit.
- At most one current version exists per entry; `entries.current_version_id` is updated in the same transaction that commits a version.
- Content hashes are SHA-256 over bytes; aggregate version hashes use the canonical algorithm in section 2.5.
- A soft-deleted entry is excluded from normal reads and search but produces a tombstone for sync.
- Authorization is applied before pagination and before search ranking results are returned.
- Public visibility never exposes drafts, deleted entries, token metadata, ACLs, or audit events.

## 2. Data model

### 2.1 PostgreSQL conventions

- PostgreSQL 16 or newer.
- Extensions: `pgcrypto` for hashing/random bytes, `citext` for case-insensitive names, and `pg_trgm` for prefix/fuzzy lookup. Use native UUIDv7 when available; otherwise generate UUIDv7 in the application.
- Timestamps are `timestamptz`, stored in UTC.
- Human identifiers use `citext` where uniqueness is case-insensitive.
- JSON uses `jsonb` and must be validated by the application before persistence.
- Primary keys are `uuid` except append-only sequence tables that use `bigint` for ordered cursors.
- All user-supplied text is UTF-8. File content is stored as `bytea`; text files must also be valid UTF-8.
- Every mutable resource has an integer `revision` used for optimistic concurrency and an `updated_at` maintained by the application.

Recommended enum types:

```sql
CREATE TYPE principal_type AS ENUM ('user', 'team');
CREATE TYPE entry_kind AS ENUM ('snippet', 'example', 'scaffold');
CREATE TYPE visibility_type AS ENUM ('private', 'team', 'public');
CREATE TYPE entry_state AS ENUM ('draft', 'published', 'archived');
CREATE TYPE file_mode AS ENUM ('text', 'binary');
CREATE TYPE acl_role AS ENUM ('viewer', 'editor', 'maintainer');
CREATE TYPE token_subject_type AS ENUM ('user', 'service');
CREATE TYPE import_state AS ENUM ('pending', 'running', 'succeeded', 'failed');
CREATE TYPE peer_mode AS ENUM ('pull', 'push', 'bidirectional');
```

### 2.5 Hashing and version commit transaction

For each file, compute `sha256(content bytes)`. Compute aggregate `content_sha256` as SHA-256 of canonical UTF-8 bytes:

```text
for files sorted by UTF-8 path bytes ascending:
  path_length_u32_be || path_utf8 || 0x00 ||
  mode_utf8 || 0x00 || media_type_utf8 || 0x00 ||
  executable_byte || file_sha256_raw_bytes
```

A version creation transaction:

1. `SELECT ... FROM entries WHERE id=$1 FOR UPDATE` and authorize editor access.
2. Verify `If-Match` against the entry revision when supplied/required.
3. Set `version_number = COALESCE(MAX(version_number),0)+1` while holding the entry lock.
4. Validate all files and the scaffold schema; calculate hashes before insertion.
5. Insert `entry_versions` and `version_files`.
6. Update `entries.current_version_id`, selected denormalized metadata, `revision=revision+1`, `updated_at`, and `updated_by`.
7. Insert one `change_events` row containing the entry ID, new version ID, and new entry revision.
8. Commit. No partially visible version is possible.

## 3. REST API contract

### 3.1 General rules

- Base path: `/api/v1`.
- HTTPS is mandatory outside localhost.
- Requests and responses use `application/json; charset=utf-8`, except archive upload/download and raw file download.
- Authentication: `Authorization: Bearer <token>` or an OIDC session cookie for first-party UI. Never accept tokens in query strings.
- Every response includes `X-Request-ID`; clients may supply a UUID in `X-Request-ID`.
- Mutable resource responses include `ETag: "r<revision>"`. `PATCH`, publish, archive, ACL mutation, and delete require `If-Match`; return `428` if absent and `412` if stale.
- POST endpoints that may be retried accept `Idempotency-Key` (1-128 printable ASCII chars). It is required for version creation, release creation, imports, renders, and peer pushes.
- Date/times are RFC 3339 UTC strings with fractional seconds.
- UUIDs are lowercase canonical strings.
- Unknown request properties are rejected with `422` except under explicitly versioned `metadata` objects.
- JSON request limit is 30 MiB; archive upload limit defaults to 250 MiB.

Standard error:

```json
{
  "error": {
    "code": "validation_failed",
    "message": "Request validation failed",
    "request_id": "0190f4a0-7f1f-7000-8000-000000000001",
    "details": [
      {"path": "/files/0/path", "code": "invalid_path", "message": "Path must be relative"}
    ]
  }
}
```

Common statuses: `200`, `201`, `202`, `204`, `400`, `401`, `403`, `404`, `409`, `410`, `412`, `413`, `415`, `422`, `428`, `429`, `500`, `503`. Return `404`, not `403`, when revealing the existence of an inaccessible private resource would leak information.

### 3.2 Pagination and field representation

Collection endpoints use keyset pagination:

```json
{
  "items": [],
  "page": {"next_cursor": "opaque-base64url", "has_more": false},
  "request_id": "..."
}
```

- `limit` defaults to 30, maximum 100.
- Cursor is an HMAC-signed, base64url JSON payload containing API version, filters hash, sort keys, and expiry. Clients must treat it as opaque.
- A cursor cannot be reused with changed filters or sort.
- Entry lists embed only current-version summary and never file bodies.
- File content in JSON is `{ "encoding":"utf-8", "content":"..." }` for text and `{ "encoding":"base64", "content":"..." }` for binary. Raw endpoints are preferred for large files.

Entry summary schema:

```json
{
  "id": "uuid",
  "slug": "http-client",
  "title": "Resilient HTTP client",
  "summary": "Retrying client with timeouts",
  "kind": "snippet",
  "visibility": "public",
  "state": "published",
  "owner": {"type": "team", "id": "uuid", "slug": "platform"},
  "category": {"id": "uuid", "path": "backend/http", "name": "HTTP"},
  "primary_language": {"slug": "python", "display_name": "Python", "lexer": "python"},
  "tags": [{"id": "uuid", "slug": "retries", "display_name": "Retries"}],
  "current_version": {"id": "uuid", "number": 4, "content_sha256": "hex", "created_at": "..."},
  "license_spdx": "MIT",
  "revision": 9,
  "created_at": "...",
  "updated_at": "..."
}
```

### 3.3 Entries and versions

#### `POST /entries`

Creates entry metadata, optionally with initial version. Requires `entries:write`.

```json
{
  "slug": "http-client",
  "title": "Resilient HTTP client",
  "summary": "Retrying client with timeouts",
  "kind": "snippet",
  "visibility": "private",
  "owner": {"type": "team", "id": "uuid"},
  "category_id": "uuid",
  "primary_language": "python",
  "tag_slugs": ["http", "retries"],
  "license_spdx": "MIT",
  "initial_version": {
    "message": "Initial version",
    "description_md": "Usage notes",
    "metadata": {"schema_version": 1},
    "files": [{
      "path": "client.py",
      "mode": "text",
      "language": "python",
      "media_type": "text/x-python",
      "content": {"encoding": "utf-8", "content": "print('hello')\n"},
      "is_template": false,
      "executable": false
    }]
  }
}
```

Returns `201` and full entry; `Location: /api/v1/entries/{id}`. `409` for owner/slug conflict, `422` for invalid language/tag/schema.

#### `GET /entries`

Filters: `q`, repeated `tag`, `tag_mode=all|any` (default all), repeated `language`, `kind`, `visibility` (only authorized values), `state`, `owner_type`, `owner_id`, `category`, `updated_after`, `sort=relevance|updated|created|title`, `limit`, `cursor`. Without `q`, default sort is `updated`; with `q`, default is `relevance`.

#### `GET /entries/{entry_id}`

Returns full metadata and caller capabilities (`can_view`, `can_edit`, `can_manage`, `can_share`). Optional `include=current_version,acl,releases`; ACL inclusion requires manage permission. `404` if absent/inaccessible, `410` only for authorized owner/admin requesting a deleted ID with `include_deleted=true`.

#### `PATCH /entries/{entry_id}`

JSON Merge Patch (`application/merge-patch+json`) over mutable metadata: title, summary, slug, visibility, state, category_id, primary_language, tag_slugs, license/homepage/repository. Owner transfer is a separate operation. Content is never patched here. Requires editor access and `If-Match`. Returns `200`.

#### `DELETE /entries/{entry_id}`

Maintainer access; soft deletes metadata and emits tombstone. Requires `If-Match`. Returns `204`. Restore: `POST /entries/{id}/restore`, admin/owner only, within configured retention (default 30 days), returns `200` or `409` if slug is now occupied.

#### `GET /entries/{entry_id}/versions`

Returns immutable version metadata newest first. `limit`, `cursor`, and optional `before_number`.

#### `POST /entries/{entry_id}/versions`

Creates a complete immutable version; does not accept partial file patches. Request has the `initial_version` shape plus optional `base_version_id`. Requires editor, `Idempotency-Key`, and `If-Match` on entry. If `base_version_id` is not current, return `409 version_conflict` unless caller explicitly sends `allow_noncurrent_base=true`; even then the new complete version becomes current. Returns `201`, new version, and updated entry ETag.

#### `GET /entries/{entry_id}/versions/{version}`

`version` may be UUID or positive version number. Returns metadata and file descriptors (path, language, size, hash), not bodies unless `include=content` and total content is under 2 MiB.

#### `GET /entries/{entry_id}/versions/{version}/files/{path}`

Path is percent-encoded by segment. Returns raw bytes, `Content-Type`, `Content-Length`, `ETag: "sha256:<hex>"`, `Content-Disposition`, and supports `Range` for binary files. `?download=true` changes disposition to attachment.

#### `GET /entries/{entry_id}/diff?from={version}&to={version}`

Returns unified text diffs and binary hash/size changes. Limit generated diff to 2 MiB/20,000 lines; otherwise return `413 diff_too_large` with file-level summary. This endpoint is informational and does not alter versions.

### 3.4 Publishing and releases

- `POST /entries/{id}/publish`: maintainer, `If-Match`, entry must have a version and valid license policy; sets state to published. Public visibility becomes anonymously readable only after publish.
- `POST /entries/{id}/archive`: maintainer, `If-Match`; hides entry from default browse while preserving direct authorized reads.
- `POST /entries/{id}/releases`: `{ "version_id":"uuid", "name":"v1.2.0", "semver":"1.2.0", "notes_md":"...", "make_default":true }`; maintainer and idempotency key; `201`.
- `GET /entries/{id}/releases`: visible to entry readers.
- `GET /entries/{id}/releases/{name}`: immutable release and version descriptor.
- `DELETE /entries/{id}/releases/{name}`: maintainer; creates tombstone, `204`; name cannot later identify different content.

### 3.5 Tags, categories, and languages

- `GET /languages`: stable list, supports `q`; public.
- `GET /tags?q=&limit=&cursor=`: only tags attached to entries visible to caller; administrators may request all.
- `POST /tags`: catalogue curator/admin, `{slug, display_name, description}`; `201`.
- `GET /categories`: returns accessible tree or `?parent_id=` children.
- `POST/PATCH/DELETE /categories`: curator/admin; deletion requires no entries/children or explicit reassignment.

### 3.6 Scaffold rendering

#### `POST /entries/{id}/render`

Renders current version, or `version_id`/`release` selected in request. Requires entry read access and `scaffolds:render`; idempotency key required.

```json
{
  "version_id": "uuid",
  "variables": {
    "project_name": "payments-api",
    "use_docker": true,
    "ports": [8080, 9090]
  },
  "output": "manifest",
  "line_endings": "lf"
}
```

`output` is `manifest`, `json`, or `zip`. `manifest` response:

```json
{
  "render_id": "uuid",
  "entry_id": "uuid",
  "version_id": "uuid",
  "input_sha256": "hex",
  "files": [
    {"path":"payments-api/README.md", "mode":"text", "media_type":"text/markdown", "size_bytes":120, "sha256":"hex", "content":{"encoding":"utf-8","content":"..."}}
  ],
  "warnings": []
}
```

ZIP output returns `application/zip` with a deterministic archive. Validation errors are `422`; generated path collisions are `409`; limits produce `413`. Rendering never executes generated code.

### 3.7 ACLs and tokens

- `GET /entries/{id}/acl`: maintainer only.
- `PUT /entries/{id}/acl/{principal_type}/{principal_id}`: maintainer; `{ "role":"editor" }`; upserts, returns `200`/`201`.
- `DELETE /entries/{id}/acl/{principal_type}/{principal_id}`: maintainer; `204`.
- `POST /entries/{id}/transfer`: current owner plus destination owner approval; `{owner:{type,id}, destination_approval_token}`. Atomic and audited.
- `GET /tokens`: current subject's token descriptors, never hashes/secrets.
- `POST /tokens`: `{name, scopes, expires_at, team_restrictions, ip_allowlist}`; returns `201` with plaintext `token` exactly once.
- `DELETE /tokens/{id}`: revokes immediately; idempotent `204`.
- `POST /tokens/{id}/rotate`: revokes old secret when new token is returned; optional short overlap up to 10 minutes for service tokens.

### 3.8 Export, import, and sync endpoints

- `POST /exports`: selects entry IDs or authorized filters; `{format:"catalogue-json|catalogue-zip", include_versions:"current|all|released", include_acl:false}`. Small exports may return `201` with download URL; otherwise `202` job.
- `GET /exports/{id}`: status and expiring download URL; only requester/admin.
- `POST /imports`: multipart archive or `{source_url, expected_sha256, mode, conflict_policy, owner}`; returns `202` import job.
- `GET /imports/{id}`: job state, item-level summary/errors.
- `POST /imports/{id}/cancel`: best-effort cancellation before commit.
- `GET /sync/changes?after={cursor}&limit={n}`: peer token only; incremental authorized change envelopes.
- `POST /sync/push`: peer token only; applies a signed batch idempotently.
- `GET /sync/snapshot`: peer token only; streaming full authorized snapshot when cursor is expired.
- `GET /sync/status`: peer/admin view of instance ID, current cursor, minimum retained cursor, protocol versions.

### 3.9 Health and operations

- `GET /health/live`: process liveness, no dependency checks.
- `GET /health/ready`: verifies DB connection, migration compatibility, and required signing key; `503` if unavailable.
- `GET /version`: build version, commit, API version, schema version; no secrets.
- Rate-limit response is `429` with `Retry-After` and standard rate-limit headers. Default authenticated limit: 600 read requests/minute and 120 writes/minute per subject; rendering/import/export have separate concurrency limits.

## 4. Scaffold template format

### 4.1 Format and safety model

The format is **Catalogue Template Language 1 (CTL1)**. It is a deliberately limited Mustache-like syntax. A scaffold version stores `template_schema.schema_version = 1`; files with `is_template=true` are parsed as CTL1. No arbitrary expressions, code execution, network access, includes outside the version, environment-variable reads, reflection, or dynamic function registration are permitted.

CTL1 applies to UTF-8 text file content and, optionally, file paths. Binary files are copied unchanged and cannot be templates. Parsing uses Unicode scalar values; output defaults to LF and UTF-8 without BOM.

### 4.2 Variable schema

`template_schema` example:

```json
{
  "schema_version": 1,
  "variables": {
    "project_name": {
      "type": "string",
      "title": "Project name",
      "description": "Lowercase project identifier",
      "required": true,
      "pattern": "^[a-z][a-z0-9-]{1,62}$",
      "min_length": 2,
      "max_length": 63
    },
    "package_name": {
      "type": "string",
      "default_from": {"variable":"project_name", "transform":"kebab_to_snake"},
      "pattern": "^[a-z][a-z0-9_]*$"
    },
    "use_docker": {"type": "boolean", "default": true},
    "runtime": {
      "type": "string",
      "enum": ["node20", "node22"],
      "default": "node22"
    },
    "port": {"type": "integer", "minimum": 1, "maximum": 65535, "default": 8080},
    "features": {
      "type": "array",
      "items": {"type":"string", "enum":["metrics","tracing","health"]},
      "unique_items": true,
      "default": ["health"]
    }
  },
  "secret_variables": [],
  "computed": {
    "class_name": {"variable":"project_name", "transform":"pascal_case"}
  },
  "limits": {"max_output_files":1000, "max_output_bytes":26214400}
}
```

Supported variable types: `string`, `integer`, `number`, `boolean`, and homogeneous `array`. V1 does not accept arbitrary object variables. Constraints are a strict JSON Schema-inspired subset: `required`, `default`, `enum`, `pattern` (RE2 syntax), string length, numeric min/max, array min/max/unique. Defaults are resolved in declaration order; cycles are rejected at publish time.

Allowed deterministic transforms: `lower`, `upper`, `snake_case`, `kebab_case`, `camel_case`, `pascal_case`, `trim`, and `kebab_to_snake` (alias retained for clarity). Transforms are locale-independent ASCII-oriented operations; non-ASCII input is preserved but not transliterated. New transforms require a CTL minor-version capability and cannot silently change existing behavior.

Secret variables are disabled by default. If enabled by deployment policy, their values must never appear in logs, hashes exposed to other users, job records, or render caches. They should generally generate references, not credentials.

### 4.3 Syntax

Variables are HTML-unescaped because output is source code:

```text
{{ project_name }}
{{ project_name | pascal_case }}
{{ port }}
```

Conditionals:

```text
{{#if use_docker}}
FROM node:22-alpine
{{else}}
# Docker disabled
{{/if}}

{{#if runtime == "node22"}}
engines: { node: ">=22" }
{{/if}}

{{#unless use_docker}}
Run locally.
{{/unless}}
```

Permitted conditions are a boolean variable, `not`/`unless`, equality or inequality between a scalar variable and a literal, and `contains(array_variable, literal)`. No arithmetic, regex, assignment, or function chaining.

Array iteration:

```text
{{#each features}}
- {{ this }}
{{else}}
- none
{{/each}}
```

Inside `each`, `this`, `@index` (zero-based), `@first`, and `@last` are available. Nested blocks are limited to depth 16. Comments are `{{! comment }}` and do not render. Literal delimiters use `{{{{` for `{{` and `}}}}` for `}}`.

Whitespace is preserved exactly. Standalone block and comment lines may use `{{~`/`~}}` to trim adjacent whitespace explicitly; there is no implicit whitespace stripping.

### 4.4 Conditional files and paths

Each template file may carry version-file metadata in `metadata.file_rules` keyed by source path:

```json
{
  "file_rules": {
    "Dockerfile.ctl": {
      "when": "use_docker",
      "output_path": "{{ project_name }}/Dockerfile",
      "strip_template_suffix": true
    },
    "src/app.ts.ctl": {
      "output_path": "{{ project_name }}/src/app.ts",
      "executable": false
    }
  }
}
```

`when` uses the same safe conditional grammar. If omitted, the file is included. `output_path` supports variable interpolation and transforms but not blocks. After rendering, normalize and validate the path using section 2.4 rules. Reject absolute paths, traversal, NUL, platform-reserved ambiguous names when target platform is specified, and collisions after Unicode/case normalization. `.ctl` is stripped only when explicitly configured or `strip_template_suffix` is true.

### 4.5 Validation and deterministic rendering

Scaffold versions are parsed and statically validated before commit and again before publishing. Validation checks all referenced variables/transforms, block balance, regex safety, defaults, output path rules, and configured limits.

For the same version, normalized variables, renderer major/minor version, and line-ending setting, rendering is byte-for-byte deterministic. Render input hash is SHA-256 of RFC 8785 canonical JSON:

```json
{"entry_id":"...","version_id":"...","renderer":"ctl1.0","variables":{},"line_endings":"lf"}
```

ZIP archives sort paths lexicographically, use fixed Unix permissions (`0755` executable, `0644` otherwise), set timestamps to the version creation time truncated to an even second, omit host-specific fields, and use a fixed compression level. Symlinks are not supported in v1.

## 5. Search implementation

### 5.1 Search document

Maintain one current search row per non-deleted entry in `entry_search`:

| Column | Type | Meaning |
|---|---|---|
| `entry_id` | `uuid` PK/FK | entry |
| `document` | `tsvector` | weighted English/simple token document |
| `title_normalized` | `text` | lowercase/unaccented title |
| `content_truncated` | `text` | bounded extracted current text for snippets |
| `language_ids` | `smallint[]` | all languages in current version |
| `tag_ids` | `uuid[]` | attached tags |
| `updated_at` | `timestamptz` | search freshness |

GIN indexes on `document`, `language_ids`, and `tag_ids`; trigram GIN on `title_normalized`. Also retain normal relational indexes on entries and `entry_tags`, because authorization/selectivity can make B-tree joins cheaper than array GIN scans.

Construct weighted document:

```sql
setweight(to_tsvector('english', coalesce(title,'')), 'A') ||
setweight(to_tsvector('english', coalesce(summary,'')), 'B') ||
setweight(to_tsvector('simple',  coalesce(tag_names,'')), 'A') ||
setweight(to_tsvector('simple',  coalesce(language_names,'')), 'B') ||
setweight(to_tsvector('english', coalesce(description_md,'')), 'C') ||
setweight(to_tsvector('simple',  coalesce(paths_and_content,'')), 'D')
```

Code content is tokenized with `simple`, not English stemming. Index at most 256 KiB of decoded text per current version and at most 64 KiB per file, in deterministic path order. Never decode/index binary files. Full file reads remain exact and are not served from the search table.

Update `entry_search` synchronously in the version/metadata transaction for predictable read-after-write. If asynchronous rebuilding is later adopted, expose `search_indexed_at` and keep metadata filters correct; v1 favors synchronous consistency.

### 5.2 Query parsing and ranking

- User query `q` is parsed with `websearch_to_tsquery('english', q)` plus a `simple` query for code identifiers.
- Reject queries over 512 characters or 64 terms.
- Combine matches from English and simple vectors.
- Ranking uses `ts_rank_cd(document, query, 32)` with weights `{0.05,0.2,0.6,1.0}` for D,C,B,A, plus bounded exact-title/prefix and freshness boosts.
- Suggested formula: `text_rank + exact_title*0.5 + title_prefix*0.15 + freshness*0.05`, where freshness decays over 180 days and cannot outrank a materially better text match.
- Stable tie-breakers are `updated_at DESC, entry_id ASC` and are encoded in cursor.
- Trigram fallback is used only when FTS returns fewer than 10 candidates and query length is at least 3. Similarity threshold starts at 0.3.

### 5.3 Tag, language, and category filtering

- Repeated `tag` values resolve slug to tag IDs. `tag_mode=all` uses containment (`tag_ids @> ARRAY[...]`); `any` uses overlap (`&&`). Unknown tag returns an empty result, not an error.
- Repeated `language` values use overlap by default. `language_mode=all` is supported for entries containing every requested language.
- Category filter includes the exact materialized path; `category=web/*` or `include_descendants=true` uses escaped path-prefix matching.
- Kind/state/owner/time filters apply relationally before final ranking.
- Filters are ANDed across dimensions.

### 5.4 Authorization in search

Build an `authorized_entries` CTE from public published entries, directly owned user entries, entries owned by caller teams, and explicit ACL grants. Join this set before ranking and pagination. Public anonymous queries include only `visibility='public' AND state='published' AND deleted_at IS NULL`.

Do not fetch broad ranked IDs and filter them in application code: that leaks counts/timing and produces short or inconsistent pages. PostgreSQL row-level security may be used as defense in depth, but application queries must still express the authorization predicate. Search facets/counts are computed only over the authorized result set and may be approximate when over a configured cost threshold.

### 5.5 Performance targets

At 1 million entries / 10 million version files:

- p95 metadata search under 300 ms for authenticated queries, excluding network.
- p95 entry lookup under 100 ms.
- Search query timeout 2 seconds; return `503 search_timeout`, not partial unauthorized data.
- Analyze search and join tables automatically; monitor GIN pending lists, query plans, index bloat, and slow queries.
- Partition `audit_events` monthly. Partition `change_events` by sequence or month only after measured need; cursor behavior must remain global.

## 6. Distribution and sync protocol

### 6.1 Bundle formats

Media types:

- `application/vnd.codecatalogue.bundle+json;version=1`
- `application/vnd.codecatalogue.bundle+zip;version=1`

Canonical JSON is RFC 8785 JSON Canonicalization Scheme encoded as UTF-8. A JSON bundle contains metadata plus base64 file bodies. A ZIP bundle is preferred for multi-file/large exports:

```text
catalogue.json
entries/<entry-id>/versions/<version-id>/files/<path>
signatures/manifest.ed25519          (optional)
```

`catalogue.json` manifest:

```json
{
  "format": "code-catalogue-bundle",
  "format_version": 1,
  "bundle_id": "uuid",
  "created_at": "2026-08-30T12:00:00Z",
  "source": {
    "instance_id": "uuid",
    "base_url": "https://catalogue.example.com",
    "name": "Example Catalogue"
  },
  "selection": {"versions":"released"},
  "entries": [{
    "id": "uuid",
    "slug": "http-client",
    "kind": "snippet",
    "title": "Resilient HTTP client",
    "summary": "...",
    "visibility": "public",
    "state": "published",
    "tags": [{"slug":"http","display_name":"HTTP"}],
    "category_path": "backend/http",
    "primary_language": "python",
    "license_spdx": "MIT",
    "versions": [{
      "id": "uuid",
      "number": 4,
      "message": "...",
      "description_md": "...",
      "content_sha256": "hex",
      "template_schema": null,
      "created_at": "...",
      "files": [{
        "path": "client.py",
        "mode": "text",
        "language": "python",
        "lexer": "python",
        "media_type": "text/x-python",
        "size_bytes": 123,
        "sha256": "hex",
        "archive_path": "entries/.../client.py",
        "is_template": false,
        "executable": false
      }]
    }],
    "releases": [{"name":"v1.0.0","semver":"1.0.0","version_id":"uuid"}]
  }]
}
```

ACLs, private ownership, audit events, tokens, emails, and sync credentials are excluded by default. An administrative backup is a separate format and not accepted by normal import endpoints.

### 6.2 Export behavior

The exporter verifies read access to every selected entry at job start and again before publishing the archive. If any explicit ID is unauthorized, the job fails rather than silently omitting it. Filter-based exports record the exact resolved IDs in the job.

Each body hash and aggregate version hash is recomputed. The manifest includes the final archive-independent bundle hash. Optional Ed25519 signature signs `SHA-256(canonical catalogue.json with signatures omitted)`. Download URLs expire (default 15 minutes), archives are encrypted at rest when staged, and jobs are deleted after 24 hours.

### 6.3 Import behavior

Import is two-phase:

1. **Validate/stage:** stream with compressed and uncompressed limits; block ZIP slip, duplicate paths, symlinks, devices, zip bombs, invalid UTF-8 metadata, hash mismatches, unknown required capabilities, and unsupported format versions. Verify signature when required. No catalogue rows are visible.
2. **Apply:** resolve languages/tags/categories under policy; authorize destination owner; then apply each entry in a transaction. For `atomic=true`, apply the complete bundle in one transaction when size permits; otherwise per-entry transactions and an itemized outcome.

Modes:

- `create`: fail if origin mapping or destination slug exists.
- `upsert-origin`: update only an existing entry with the same trusted `(origin_instance_id, origin_entry_id)`; never match solely by slug.
- `fork`: create a new local entry with new IDs and `forked_from` provenance; imported versions retain source IDs.
- `mirror`: peer-admin only; local edits prohibited and remote deletions propagate.

Conflict policies are `reject`, `rename` (append deterministic suffix), or `fork`; overwrite-by-slug is not supported. Duplicate source version IDs/content hashes are idempotently skipped. Imported versions are immutable and numbered locally in arrival order; `source_version_id` preserves remote identity. Imported visibility is capped by caller request, source visibility, peer policy, and destination owner policy—the most restrictive wins. Imported entries default to private unless a trusted peer rule explicitly permits public.

### 6.4 Incremental instance synchronization

Protocol version is negotiated using `X-Code-Catalogue-Sync: 1`; peers expose their stable instance ID and Ed25519 public key. Transport uses TLS 1.2+; production peers should use mTLS or a peer-scoped bearer token plus signed batches. Tokens require `sync:pull` and/or `sync:push` and namespace restrictions.

Pull sequence:

1. Consumer calls `GET /sync/status` and checks protocol, source instance ID, `current_cursor`, and `minimum_cursor`.
2. Consumer calls `GET /sync/changes?after=N&limit=500`.
3. Producer returns events strictly ordered by local `sequence`, `next_cursor`, `has_more`, and a detached response signature.
4. Consumer verifies TLS identity, instance ID, signature, event IDs, hashes, namespace, and visibility policy.
5. Consumer applies a batch transactionally, recording `(origin_instance_id, origin_event_id)` before advancing peer cursor.
6. Consumer continues until `has_more=false`. Cursor advances only after durable apply.

Envelope:

```json
{
  "protocol_version": 1,
  "source_instance_id": "uuid",
  "after": 1042,
  "next_cursor": 1099,
  "minimum_cursor": 800,
  "has_more": false,
  "events": [{
    "sequence": 1043,
    "event_id": "uuid",
    "operation": "update",
    "resource_type": "entry",
    "resource_id": "uuid",
    "entry_id": "uuid",
    "origin": {"instance_id":"uuid","event_id":"uuid"},
    "occurred_at": "...",
    "payload": {"entry": {}, "versions": []},
    "payload_sha256": "hex"
  }],
  "signature": {"key_id":"...","algorithm":"Ed25519","value":"base64url"}
}
```

Events must contain enough immutable content or authenticated URLs to fetch it by hash. Fetch URLs are short-lived and peer-authorized. A push uses the same envelope at `POST /sync/push`; successful response reports accepted, duplicate, rejected, and resulting cursor/event IDs. Partial rejection is allowed only per entry; events for one entry preserve order.

### 6.5 Tombstones, retention, and snapshots

Delete events contain origin entry ID, last known revision/hash, deletion time, and tombstone ID, never file bodies. Mirror peers apply deletion. Fork/upsert peers follow configured policy (default: mark origin deleted but retain local fork). Tombstones are retained at least one year or permanently for release names.

If `after < minimum_cursor`, return `410 cursor_expired` with snapshot URL/capability. Snapshot is a signed ZIP bundle plus `snapshot_cursor`. Consumer applies snapshot and then resumes changes after that cursor. Snapshot application does not delete local-only entries; mirrors reconcile origin-mapped entries absent from the snapshot according to explicit deletion markers or authoritative snapshot mode.

### 6.6 Conflict and loop prevention

- Deduplicate on `(origin_instance_id, origin_event_id)` and source version IDs.
- Never re-emit an imported event back to the immediate source.
- Preserve root origin in relayed events and keep a bounded `via` list; reject own instance ID in `via`.
- `mirror`: remote is authoritative; local content writes return `409 mirror_read_only`.
- `fork`: first divergent local edit detaches future automatic content updates unless a maintainer reconciles.
- `reject`: sync records conflict and stops advancing past that entry batch; other independent entry batches may continue.
- Metadata merge is not last-write-wins across instances. Ownership/ACL/visibility are local policy; content conflicts produce separate versions/forks or rejection.

## 7. Access control model

### 7.1 Principals, roles, and permissions

Principals are authenticated users, teams (through membership), service tokens, anonymous callers, and instance peers. Entry roles map to permissions:

| Role | Read | Render/export | Create version/edit metadata | Publish/release | Manage ACL/delete/transfer |
|---|---:|---:|---:|---:|---:|
| viewer | yes | yes | no | no | no |
| editor | yes | yes | yes | no | no |
| maintainer | yes | yes | yes | yes | yes, except transfer needs owner |
| owner | yes | yes | yes | yes | yes |

Team membership maps: team `member` receives owner-team viewer baseline, `maintainer` receives editor baseline, and team `owner` receives owner authority. Deployments may make this mapping stricter but not broader without explicit documentation. Direct ACL grants can increase access but cannot reduce owner-derived access.

### 7.2 Visibility and state

- **private:** only owner authority and explicit ACL principals.
- **team:** owner team members plus explicit ACL principals. Only team-owned entries may use this value.
- **public:** anonymously readable only when state is `published`; authenticated ACL users can access a public draft according to role.
- **draft:** never anonymously visible.
- **archived:** omitted from browse/search defaults; direct reads still follow visibility and ACL.
- **deleted:** unavailable except retention restore/admin workflows.

Changing private/team to public requires maintainer permission, published state or an atomic publish request, a current version, successful scaffold validation, and license-policy compliance. Changing owner or ACL is audited.

### 7.3 Authorization algorithm

For action `A` on entry `E`:

1. Reject disabled/expired/revoked credentials and enforce token scopes/IP restrictions.
2. If anonymous, allow only read/export of public, published, non-deleted content; rendering may be separately disabled for anonymous callers.
3. Site admin may act subject to an audited break-glass policy; admin reads of private content must be logged.
4. Derive owner role from user owner or owner-team membership.
5. Load direct user ACL and ACLs for caller teams; choose highest role.
6. Apply visibility baseline without exceeding state rules.
7. Map effective role to required permission and token scope.
8. Apply resource-specific restrictions (mirror read-only, transfer approval, license policy).
9. Deny by default.

Authorization information should be cached no longer than 60 seconds and invalidated on membership/ACL/token changes. Sensitive writes must query current DB state, not rely solely on cache.

### 7.4 Token format and scopes

Token display format:

```text
ccat_<token-id-base32>_<32-random-bytes-base64url>
```

Parse token ID for indexed lookup, then verify secret with Argon2id using deployment-calibrated parameters (target 100-250 ms) and constant-time comparison. Log only token ID/prefix. Require at least 256 bits of CSPRNG entropy.

Scopes:

- `entries:read`, `entries:write`, `entries:manage`
- `scaffolds:render`
- `exports:read`, `imports:write`
- `teams:read`, `teams:manage`
- `tokens:manage`
- `sync:pull`, `sync:push`
- `admin:*` (site administrators only)

Scopes are necessary but not sufficient: entry/team authorization still applies. Service tokens have explicit owner/team grants and no implicit human identity. Tokens are shown once, revocable immediately, expiry is recommended (maximum one year by default), and token create/use/revoke is audited.

### 7.5 Security requirements

- Use OIDC Authorization Code + PKCE for interactive login. Validate issuer, audience, nonce, state, signature, and clock skew.
- Protect cookie sessions with Secure, HttpOnly, SameSite=Lax/Strict, CSRF tokens on unsafe methods, and short idle lifetime.
- Encrypt external credentials/signing private keys using a KMS or mounted secret; never store in manifests or DB plaintext.
- Sanitize Markdown/HTML at render time with a restrictive allowlist. Store original Markdown, but never trust it.
- Serve code as text/plain or an explicit safe media type with `X-Content-Type-Options: nosniff`; never execute previews in the application origin. If preview is added, isolate on a sandbox origin with strict CSP.
- Validate URLs and block server-side request forgery on imports: HTTPS only by default, DNS/IP revalidation, deny private/link-local/metadata ranges unless peer allowlisted, cap redirects/size/time.
- Audit authentication failures (sampled), token lifecycle, ACL/owner changes, imports, sync, publish, releases, deletion, restore, and admin access.
- Backups include DB and signing identity, are encrypted, tested quarterly, and have documented RPO/RTO.

## 8. Migration and deployment plan

### 8.1 Service components

1. **API service:** stateless REST API, authorization, validation, rendering orchestration.
2. **Worker:** import/export jobs, search rebuilds, archive generation, sync scheduling, retention cleanup.
3. **PostgreSQL 16+:** source of truth.
4. **Object storage (optional but recommended):** staged imports/exports and large generated archives; S3-compatible with server-side encryption and lifecycle rules.
5. **OIDC provider/KMS:** production identity and secret management.
6. **Reverse proxy/load balancer:** TLS termination, body/rate limits, request IDs.

API and worker use the same versioned domain library for hashing, CTL parsing, bundle validation, authorization semantics, and protocol schemas.

### 8.2 Initial schema migration sequence

Use a migration tool with a `schema_migrations(version bigint primary key, checksum text, applied_at timestamptz, duration_ms integer)` table and advisory lock. Never edit an applied migration; append corrective migrations.

1. `0001_extensions_types`: extensions and enum types.
2. `0002_identity`: users, teams, memberships, API tokens.
3. `0003_taxonomy`: languages, tags, categories; seed canonical languages.

### 8.3 Deployment phases

#### Phase 0: foundation

- Provision PostgreSQL with TLS, PITR/WAL archiving, encrypted disks, monitoring, and least-privilege roles (`catalogue_migrator`, `catalogue_app`, `catalogue_readonly`).

- Backfill/verify search rows before enabling `/entries?q=`.
- Acceptance: version hash fixtures pass across API and worker; unauthorized-entry test matrix passes; restore from backup succeeds.

#### Phase 2: scaffolds and releases

- Deploy CTL1 parser/validator and deterministic renderer behind `scaffolds_enabled`.
- Run golden fixtures for conditionals, loops, transforms, paths, LF/CRLF, Unicode, limits, and deterministic ZIP hashes.

- Keep rendering concurrency-limited; no code execution runtime is deployed.

#### Phase 3: distribution

- Enable signed exports and staged imports behind separate flags.
- Begin with public entries and `fork` conflict policy only.
- Test malicious archives, signature failures, hash failures, SSRF, ZIP bomb/path traversal, and interrupted jobs.

#### Phase 4: peer sync

### 8.4 Zero-downtime migration policy

Use expand/migrate/contract:

1. **Expand:** add nullable columns/tables/indexes compatible with old and new application versions.
2. **Deploy dual-compatible code:** write both representations when needed and read with fallback.
3. **Backfill:** bounded batches ordered by PK, commit frequently, throttle on replication lag, record resumable cursor.
4. **Validate:** compare counts/hashes; add `NOT VALID` constraints then `VALIDATE CONSTRAINT`.
5. **Switch reads:** feature flag/canary, then all nodes.
6. **Contract:** remove old columns/behavior only after at least one rollback window and no old binaries remain.

Do not add a non-null column with a volatile/default table rewrite to large tables in one step. Avoid enum value removal; use replacement types if necessary. Schema compatibility rule: application release N supports database schemas N and N-1 during rolling deployment.

### 8.7 Backup, restore, retention, and disaster recovery

- PostgreSQL: daily base backup plus continuous WAL; default RPO 5 minutes, RTO 4 hours.
- Object storage: versioning/lifecycle and inventory; bundles are reconstructable from DB where bodies are DB-resident.
- Back up the stable instance ID and signing keys separately under KMS; key loss requires explicit peer re-trust, not silent identity replacement.
- Quarterly restore drill verifies row counts, sampled content hashes, current-version links, search rebuild, release links, API readiness, and sync identity.
- Soft-deleted entries purge after policy (default 30 days) only if no legal hold and no retained release/provenance requirement. Purge emits/retains tombstones.
- Audit retention defaults to 365 days; sync changes retain at least 90 days plus peer watermark constraints; expired job artifacts default to 24 hours.

### 8.8 Rollback

Application rollback is supported while schema remains in expanded dual-compatible state. Database down-migrations are not automatic in production. For a faulty data migration: stop affected writes with feature flags, deploy corrective forward migration, restore from PITR only when corruption cannot be repaired and after preserving forensic evidence. Sync/import features can be independently disabled without disabling core reads.

### 8.9 Acceptance criteria

The first production release is acceptable when all of the following are verified:

1. CRUD and authorization matrix covers anonymous, user owner, team roles, direct ACL roles, admin, revoked/expired token, draft/public/private/team/archive/delete states.
2. Concurrent version creation yields unique sequential numbers and no orphan files/current pointers.
3. Editing always produces immutable prior content with reproducible hashes.
4. Search authorization, FTS, all/any tags, language, category, pagination, and stable ranking pass integration tests on realistic data.
5. CTL golden tests are byte deterministic and malicious templates cannot execute code, escape paths, or exceed limits.
6. JSON/ZIP round trips preserve IDs/provenance, hashes, releases, executable bits, and UTF-8 bytes under documented modes.
7. Import rejects traversal, symlinks, duplicate paths, malformed manifests, signature/hash errors, SSRF targets, and decompression bombs.
8. Sync survives duplicate delivery, reorder rejection, process crash before/after commit, cursor expiry/snapshot, deletion, conflict, and A→B→A loops.
9. API contract is published as OpenAPI 3.1 generated/validated from the same schemas; compatibility tests reject undocumented breaking changes.
10. Load tests meet section 5.5 targets; backup restore and rolling upgrade/rollback drills succeed.

## B.2 Isolation boundary

V1 tenancy is deliberately **owner-namespace tenancy**, not organization tenancy. A namespace is exactly one user principal or team principal. Entry slug uniqueness, quotas, export selection, search authorization, object prefixes, signed URLs, audit visibility, and encryption-context labels are scoped to the owner principal ID. There is no implicit organization boundary and no cross-namespace access: sharing occurs only through public published visibility or an explicit `entry_acl` row. Team membership creates authority only in that team namespace. Database queries for non-public resources MUST begin from an authorized-principal set and include owner/ACL predicates before filtering, ranking, counting, or artifact lookup. Object keys MUST include immutable resource IDs and owner principal ID; signed URLs are bound to both. Cross-namespace transfer is the sole ownership move and follows B.8.7. Future organization tenancy requires API/schema v2.

## B.3 Principal, identity, token, and ACL schema

### B.3.1 General principals

Replace polymorphic identity with:

```sql
CREATE TYPE principal_kind AS ENUM ('user','team','service','peer');
CREATE TABLE principals (
  id uuid PRIMARY KEY,
  kind principal_kind NOT NULL,
  display_name text NOT NULL,
  disabled_at timestamptz,
  revision integer NOT NULL DEFAULT 1 CHECK (revision > 0),
  created_at timestamptz NOT NULL DEFAULT now(),
  updated_at timestamptz NOT NULL DEFAULT now()
);
```

`users.principal_id`, `teams.principal_id`, `service_principals.principal_id`, and `instances.principal_id` are `UNIQUE NOT NULL REFERENCES principals(id) ON DELETE RESTRICT`; a deferred constraint trigger proves kind equality. `service_principals(id uuid PK, principal_id uuid UNIQUE NOT NULL, service_name citext UNIQUE NOT NULL, created_by_principal_id uuid NOT NULL REFERENCES principals ON DELETE RESTRICT, revision, created_at, updated_at, disabled_at)` and peer principals are explicit. Human-only profile attributes remain in `users`.

All actor/creator/updater columns, including `entry_versions.created_by_principal_id`, imports, exports, releases, audit, change events, and ACL changes, reference `principals(id) ON DELETE RESTRICT`; they are never user-only. System work runs as a dedicated disabled-for-login service principal. Disabled principals retain referential identity but authorize nothing. Hard deletion is forbidden while referenced; anonymization preserves the principal ID and kind.

`entry_acl(entry_id, principal_id, role, revision, created_by_principal_id, created_at, updated_at)` has PK `(entry_id,principal_id)`, both FKs `ON DELETE CASCADE` for entry and `ON DELETE RESTRICT` for principal, and reverse index `(principal_id,entry_id)`. Users, teams, services, and peers can therefore receive grants. Owner authority is represented by `entries.owner_principal_id REFERENCES principals ON DELETE RESTRICT` and a trigger limits owner kind to user/team/service; peer ownership is forbidden.

### B.3.2 Teams and token restrictions

`team_memberships` references team and user principals, uses `ON DELETE CASCADE`, has `revision`, `updated_at`, and checked role. At least one active owner is required; a deferred constraint trigger checks this after each membership transaction.

Replace array token fields with:

```text
api_tokens(id, subject_principal_id FK principals RESTRICT, name, verifier_key_id,
 verifier, secret_prefix, expires_at, overlap_expires_at, revoked_at,
 revision, created_at, updated_at, last_used_at)
api_token_scopes(token_id FK CASCADE, scope PK component; CHECK scope in registry)
api_token_teams(token_id FK CASCADE, team_principal_id FK principals RESTRICT;
 PK(token_id,team_principal_id), kind trigger requires team)
api_token_cidrs(token_id FK CASCADE, network cidr; PK(token_id,network))
```

Maximums are 32 scopes, 100 teams, and 64 CIDRs. CIDRs are stored via PostgreSQL `cidr`, canonicalized by `network()`, duplicates rejected; overlapping ranges are permitted but do not broaden beyond their union. Empty team rows mean no team authority for service/peer principals and normal current memberships for user principals. Token effective authority is the intersection of subject authority, listed teams (if any), scopes, IP, expiry, and current revocation. Token issuance cannot delegate any scope/team/entry authority or expiry beyond the issuer's delegable authority. Service-principal creation or grant requires owner plus `tokens:manage`; `admin:*` requires interactive MFA site admin.

API-token verification uses Appendix C's keyed HMAC verifier, not per-request Argon2id. Revocation and sensitive writes consult the authoritative row. Read caches are keyed by token ID+revision and receive transactional outbox invalidations over a durable pub/sub channel; nodes retry until acknowledged, expire entries after 60 seconds, and alert if invalidation is older than five seconds. On channel failure, sensitive operations fail closed to DB reads.

## B.4 Corrected relational model and integrity

### B.4.1 Revision rule and FK policy

Every mutable table has `revision integer NOT NULL DEFAULT 1 CHECK(revision>0)` and `updated_at timestamptz NOT NULL`; mutation increments revision exactly once in the transaction. This includes users, principals, teams, memberships, languages, tags, categories, entries, ACLs, API tokens, service principals, sync peers, namespace policies, imports, exports, render jobs/caches, artifacts, legal holds, and transfer approvals. Append-only immutable rows (`entry_versions`, `version_files`, releases before tombstoning, audit/change/tombstones) do not have revision and cannot be PATCHed. Mutable API responses have `ETag:"r<revision>"`; every mutation requires `If-Match`, except idempotent token revocation which still atomically increments revision if first revoked.

Unless explicitly overridden: required ownership/actor FKs are `NOT NULL ON DELETE RESTRICT`; optional taxonomy FKs are nullable `ON DELETE SET NULL`; join rows use `ON DELETE CASCADE`; provenance and immutable-content FKs use `ON DELETE RESTRICT`; all FKs use `ON UPDATE RESTRICT`. Circular commit pointers are `DEFERRABLE INITIALLY DEFERRED`. No implementation may choose different actions.

### B.4.2 Entry/version/release integrity

Add `UNIQUE(entry_id,id)` to `entry_versions` and `releases`. Store `entries.current_version_entry_id` and `default_release_entry_id`, each constrained equal to `entries.id`, then create composite FKs:

```sql
FOREIGN KEY (current_version_entry_id,current_version_id)
 REFERENCES entry_versions(entry_id,id) DEFERRABLE INITIALLY DEFERRED;
FOREIGN KEY (default_release_entry_id,default_release_id)
 REFERENCES releases(entry_id,id) DEFERRABLE INITIALLY DEFERRED;
FOREIGN KEY (entry_id,version_id)
 REFERENCES entry_versions(entry_id,id) ON DELETE RESTRICT;
```

Nullable pointer column pairs are both-null or both-non-null. This proves every pointer belongs to the same entry. Release deletion is a transaction that inserts immutable `release_tombstones(id,entry_id,name,former_release_id,former_version_id,deleted_by_principal_id,deleted_at)` with `UNIQUE(entry_id,name)`, clears the default pointer if selected, deletes the release, emits a tombstone event, and commits. Creation checks both live and tombstone names; names are permanently reserved. If the default is deleted, no automatic replacement occurs.

Remote versions use both `source_instance_id NOT NULL REFERENCES instances(id) ON DELETE RESTRICT` and `source_version_id`; imported rows require both and have `UNIQUE(source_instance_id,source_version_id)`. Local rows have both null. An entry's origin may differ from a relayed version's source; root source is never inferred from entry origin.

### B.4.3 Version-file checks and purge privilege

`version_files` includes checks `size_bytes>=0`, `octet_length(content)=size_bytes`, `octet_length(sha256)=32`, `mode='binary' => is_template=false`, and `is_template=true => mode='text'`. `entry_versions` checks `octet_length(content_sha256)=32`. The transaction validator MUST verify UTF-8 for text, normalized paths, media-type syntax, lexer/language references, per-file SHA-256, and aggregate SHA-256 before insert; a deferred trigger recomputes cheap byte length/hash checks. Direct UPDATE/DELETE on versions/files is revoked from application and worker roles.

Hard purge is only `catalogue_purge.purge_entry(uuid,reason)` owned by a NOLOGIN role, `SECURITY DEFINER SET search_path=pg_catalog,catalogue_purge`, with fully qualified names. It checks retention, legal holds, releases, provenance and tombstone durability, locks the entry, writes immutable audit, and deletes in one transaction. Only a dedicated retention role may execute it; application roles cannot disable triggers or set replication role.

### B.4.4 Categories and taxonomy

Category slugs exclude `/`, backslash, `%`, control characters, and dot segments and match the entry-slug grammar. `path` is NFC lowercased slash-joined slugs. A deferred recursive constraint trigger rejects self-parenting, cycles, and depth over 8 and locks the moved subtree. Moves rewrite all descendants atomically. Use `CREATE INDEX categories_path_prefix_idx ON categories(path text_pattern_ops)`; descendant predicates are `path=$1 OR path LIKE escape_like($1)||'/%'` with bound parameters.

Language slug and aliases share one global normalized namespace: ASCII lowercase, `_` converted to `-`, trim ASCII whitespace, then slug grammar. `language_names(normalized_name PRIMARY KEY, language_id FK CASCADE, kind)` enforces collisions. Language CRUD is curator-only, revisioned; deletion returns `409 language_in_use` unless a replacement is provided and all references are reassigned in one serializable transaction. Category delete accepts `{reassign_entries_to, reparent_children_to}` (nullable UUIDs); it locks the category/subtree and affected entries, validates depth/cycles, reassigns all or none, then deletes. Omission when dependencies exist returns `409 category_not_empty`.

### B.4.5 Operational resources

Use a common checked state machine:

```text
jobs(id, kind import|export|render|search-rebuild, owner_principal_id, state,
 requested_at, available_at, started_at, completed_at, cancelled_at,
 attempt_count, max_attempts, lease_owner, lease_expires_at, heartbeat_at,
 progress_current, progress_total, error_code, error_detail_redacted,
 request_artifact_id, result_artifact_id, expires_at, revision, updated_at)
artifacts(id, owner_principal_id, kind, storage_backend, object_key nullable,
 body bytea nullable, size_bytes, sha256, media_type, filename,
 encryption_context, created_at, expires_at, deleted_at, revision, updated_at)
imports(job_id UNIQUE FK jobs CASCADE, source_type, source_uri, expected_sha256,
 mode, conflict_policy, requested_atomic, accepted_atomic, options, summary)
exports(job_id UNIQUE FK jobs CASCADE, format, selection, resolved_entry_ids,
 include_versions, summary)
render_jobs(job_id UNIQUE FK jobs CASCADE, entry_id, version_id,
 renderer_version, output, target_platform, line_endings, public_input_digest)
render_cache(cache_key bytea PK, version_id, renderer_version, artifact_id,
 created_at, expires_at, revision, updated_at)
```

Exactly one of `artifacts.body` and `object_key` is set; lengths/hashes are checked. Object writes are staged under random keys, checksum-verified, promoted before the DB reference commits, and lifecycle deletion is retried through an outbox. Workers claim with `FOR UPDATE SKIP LOCKED`, lease 60 seconds, heartbeat every 20, retry transient errors with exponential jitter up to five attempts, and recover expired leases. Cancellation is revisioned and follows Appendix C. Jobs/artifacts are owner-authorized, expire after 24 hours by default, and expose checksums. Binary idempotent responses store `artifact_id` and a replay descriptor rather than JSON bodies.

`idempotency_keys(subject_principal_id,key,request_sha256,response_status,response_headers,response_json nullable,artifact_id nullable,resource_location nullable,created_at,expires_at)` permits exactly one replay representation. Request hash is SHA-256 of method, canonical path/query, media type, and canonical JSON or uploaded-byte digest. Same key/different hash returns `409 idempotency_key_reused`; same hash replays exact status/headers/body or redirects to the same job/artifact.

`legal_holds(id, scope_type, scope_id, reason, created_by_principal_id, released_by_principal_id, created_at,released_at,revision,updated_at)` is admin/compliance-only and audited. Purge eligibility is: deletion retention elapsed AND no active hold covering entry/version/artifact/audit subject AND no live release AND all required origin/tombstone retention is materialized. Otherwise purge records the blocking reason. Releases retain their versions until release deletion; permanent release tombstones survive purge. Restore never resurrects a deleted release name.

## B.5 Large version staged upload

JSON inline creation is limited to 20 MiB decoded total so worst-case base64 plus JSON stays below 30 MiB. Versions up to the legal 25 MiB decoded limit use staged upload:

1. `POST /entries/{id}/version-uploads` (`entries:write`, editor, `If-Match`, `Idempotency-Key`) with `{base_version_id,message,description_md,metadata,template_schema,files:[{path,mode,language,media_type,size_bytes,sha256,is_template,executable,file_rule}]}`. It validates the complete manifest and returns `201 {upload_id,revision,expires_at,files:[{file_id,put_url}]}`. Upload expires in one hour.
2. Each file is uploaded once via `PUT /version-uploads/{upload_id}/files/{file_id}` with raw bytes, `Content-Length`, `Digest: sha-256=...`, and `If-Match` upload ETag. Multipart object-store upload is an internal optimization. Size/hash mismatch returns `422 upload_digest_mismatch` and does not mark complete.
3. `POST /version-uploads/{upload_id}/commit` with upload `If-Match` and idempotency key revalidates every staged object, entry revision/base, CTL schema/rules and 5 MiB/file, 25 MiB/version, 1,000-file limits. It inserts the immutable version/files (streaming staged bytes), current pointer, search row and event in one DB transaction. Failure creates no visible version. Staged objects are deleted after commit or expiry.
4. `DELETE /version-uploads/{upload_id}` cancels before commit. Status exposes no file bodies. Authorization is rechecked on every operation.

The complete `VersionCreate` schema contains `message`, `description_md`, `metadata`, nullable `template_schema`, and files whose descriptors include nullable `file_rule {when,output_path,strip_template_suffix,executable}`. For scaffold entries `template_schema` is required and every file rule is validated; for other kinds it and `is_template/file_rule` are forbidden. `POST /entries` uses exactly this schema for `initial_version` and requires `Idempotency-Key`.

Authorization changes invalidate the authorization generation; deleted rows may create omissions but never duplicates.

## B.8 HTTP edge protocols

### B.8.1 Version locators and paths

`{locator}` is either canonical lowercase UUID (contains hyphens) or version number grammar `[1-9][0-9]{0,9}`. Leading zeros, `+`, whitespace, overflow, malformed UUID, and UUID-like alternatives return `404 invalid_version_locator`; releases are addressed only under `/releases/{name}`, so UUID-shaped release names are unambiguous. No redirects normalize locators.

Raw file routing MUST preserve the raw request target through the proxy. Split on literal `/`, reject empty segments, validate `%` triplets, percent-decode each segment exactly once to bytes, reject decoded `/`, backslash, NUL, dot segments, invalid UTF-8, non-NFC, controls, and any segment whose re-encoding is not canonical uppercase-percent encoding for non-unreserved bytes. `%25` followed by hex remains a literal percent sequence and is not decoded again. Noncanonical forms return `400 invalid_file_path`, never redirect. Proxy normalization/encoded-slash decoding must be disabled; readiness fails if a conformance probe changes the raw path.

Raw bodies support one byte range for every mode. Send `Accept-Ranges: bytes`; valid range returns `206` and `Content-Range`, unsatisfiable/multiple ranges return `416 bytes */length`. `If-Range` accepts the immutable SHA-256 ETag; mismatch sends full `200`.

### B.8.2 Render selection and representations

`RenderRequest={version_id?,release?,variables,output,target_platform,line_endings}` has `oneOf` preventing both selectors. If neither: use live default release if set, otherwise current version; absent version is `409 no_renderable_version`. `manifest` omits bodies and lists descriptors; `json` includes bodies under JSON limits; `zip` is Appendix C canonical ZIP. JSON/manifest are `application/json`; ZIP is `application/zip` with safe disposition, Digest, ETag, and artifact replay. Same idempotency key returns identical JSON or the same immutable artifact/job. CTL1 secrets are forbidden, so public `input_sha256` covers only normalized non-secret inputs.

### B.8.3 Headers and caches

Authorization-sensitive JSON/raw/artifact/token responses use `Cache-Control: private,no-store` and `Vary: Authorization,Cookie`; token plaintext additionally `Pragma:no-cache`. Public immutable version bodies may use `public,max-age=300,must-revalidate`; mutable entry responses use `no-cache`. All body downloads use `X-Content-Type-Options:nosniff`, `Referrer-Policy:no-referrer`; UI pages use `Content-Security-Policy: default-src 'self'; object-src 'none'; base-uri 'none'; frame-ancestors 'none'`. Content-Disposition uses RFC 6266/RFC 5987 library encoding after stripping CR/LF/NUL/control/separators, never raw concatenation.

Visibility/state/delete changes revoke future signed URLs synchronously and enqueue CDN/object purge. Origin authorization denies immediately; purge failure alerts. Signed URLs expire in 15 minutes and bind artifact ID, owner principal, disposition, and checksum.

### B.8.4 Anonymous controls and owner-team meaning

Flags `ANONYMOUS_READ`, `ANONYMOUS_EXPORT`, and `ANONYMOUS_RENDER` are independent; latter two default false. Only public, published, nondeleted entries qualify. Disabled operations return `404 feature_disabled`. Anonymous outputs obey Appendix C rate/concurrency/size limits and never include private metadata. Team `member`, `maintainer`, and `owner` mappings are owner-derived authority for private team-owned entries: viewer, editor, and owner respectively; explicit ACL can raise but never lower it.

### B.8.5 Break glass

Break glass is disabled by default. Eligible site admins use an interactive MFA session, enter reason and ticket, obtain approval from a second admin, and receive a 15-minute action-scoped grant. Read and mutation permissions are separately approved; transfer, token secret access, signing-key changes, and audit deletion remain forbidden. Every request writes immutable before/after audit and notifies namespace owners; grants can be revoked immediately and are reviewed within one business day.

### B.8.6 Transfer approval protocol

`POST /entries/{id}/transfer-approvals` is called by an authorized destination owner with `{destination_owner_principal_id,entry_revision,expires_in_seconds<=600}`. It creates `transfer_approvals(id,entry_id,entry_revision,destination_owner_principal_id,issued_to_principal_id,nonce_sha256,expires_at,consumed_at,revoked_at,revision,...)` and returns once:

```text
ccat_xfer1.<base64url(RFC8785 claims)>.<base64url(HMAC-SHA-256(K_transfer,claims))>
```

Claims are `{v:1,kid,jti,entry_id,entry_revision,destination_owner_principal_id,issued_to_principal_id,iat,exp,nonce}`; `kid` is the active transfer-key identifier used to select `K_transfer`. The transfer caller must be current owner; service verifies HMAC/key ID, exact entry/revision/destination, destination approver's current owner authority, expiry, revocation, and unused JTI. Transfer and `consumed_at` commit atomically; replay is `409 approval_consumed`, stale binding `412`, expiry `410`. Issuance/revocation/use are audited; approval tokens are never logged and cannot approve another entry/revision/destination. `K_transfer` is held in KMS/secret storage, never in the database. Rotation creates a new random key and `kid`, makes it active for issuance, and retains old keys for verification only until the last token they signed has expired plus the 60-second clock-skew allowance; at most one key issues tokens at a time. Emergency revocation disables verification by that `kid` immediately and invalidates all affected outstanding approvals. Unknown, revoked, or retired `kid` values fail closed. Rotation and revocation require two-admin approval and are audited.

## 2. Distribution and bundle clauses

### 2.1 Bundle identity and hash

1. Every manifest **MUST** contain:
   ```json
   {
     "hash_algorithm": "sha-256",
     "bundle_sha256": "<64 lowercase hex characters>"
   }
   ```
2. Define `unsigned_manifest` as the manifest with `bundle_sha256` and every signature field removed. The archive-independent bundle digest is:
   ```text
   SHA-256(
     "CCAT-BUNDLE-1\n" ||
     RFC8785(unsigned_manifest)
   )
   ```
   where the prefix is ASCII and the canonical manifest is UTF-8.
3. Every file descriptor **MUST** include its byte length and SHA-256 digest. Importers **MUST** validate every body against both fields before validating `bundle_sha256`. Therefore the bundle digest commits to file bytes through the signed manifest descriptors without depending on ZIP container bytes.
4. A signature **MUST** sign:
   ```text
   "CCAT-BUNDLE-SIGNATURE-1\n" || bundle_digest_raw_32_bytes
   ```
5. Exporters and importers **MUST** publish and pass common manifest, digest, and signature vectors, including empty, Unicode-path, binary-file, and multi-version bundles.

### 2.2 Canonical ZIP profile

1. Bundle ZIP archives **MUST**:
   - contain exactly one `catalogue.json` member and exactly the members referenced by manifest `archive_path` fields;
   - contain no directory entries, unreferenced members, duplicate decoded names, comments, encryption, data descriptors, ZIP64 records, or extra fields;
   - use UTF-8 member names with general-purpose flag bit 11 set and all other flags clear;
   - use method 0 (`STORE`) so archive bytes do not depend on a DEFLATE implementation;
   - set “version made by” to Unix/3.0 (`0x031e`) and “version needed” to 1.0;
   - set DOS timestamps from the version creation time in UTC, truncating seconds to an even value;
   - set Unix mode in external attributes to `0100755 << 16` for executable files and `0100644 << 16` otherwise;
   - set internal attributes to zero and compute standard IEEE CRC-32 over member bytes;
   - order local records and central-directory records by unsigned UTF-8 filename bytes, with `catalogue.json` participating in the same ordering.
2. `catalogue.json` **MUST** be RFC 8785 canonical UTF-8 without a BOM.
3. Archive paths **MUST** be NFC-normalized POSIX relative paths. Importers **MUST** reject names containing NUL, backslash, absolute-path syntax, empty/`.`/`..` segments, invalid UTF-8, or percent-encoded alternate spellings.
4. Importers **MUST** reject collisions after each of:
   - exact UTF-8-byte comparison;
   - Unicode NFC plus full Unicode case folding;
   - Windows comparison after removing trailing spaces/dots and rejecting device names and alternate-data-stream colons.
5. Failure of any profile rule **MUST** reject the complete archive before catalogue rows are written.

### 2.3 Archive resource ceilings

Unless a deployment configures stricter values, validation **MUST** enforce:

| Limit | Default |
|---|---:|
| compressed request bytes | 250 MiB |
| total uncompressed bytes | 1 GiB |
| members | 10,000 |
| bytes per member | 25 MiB |
| filename bytes | 1,024 |
| path segments | 128 |
| compression ratio per member | 100:1 |
| aggregate compression ratio | 50:1 |
| manifest bytes | 16 MiB |
| validation wall time | 120 seconds |
| source-URL redirects | 3 |
| source-URL connect/read timeout | 5/30 seconds |

Nested archives, symlinks, hard links, sparse members, devices, FIFOs, encrypted members, and unsupported compression methods **MUST** be rejected. Crossing any ceiling **MUST** abort staging, delete staged bytes, and return `413 archive_limit_exceeded` with the exceeded limit but not sensitive filesystem details.

### 2.4 Import atomicity and cancellation

1. `POST /imports` **MUST** accept `atomic` as `required`, `preferred`, or `per-entry`.
2. Before returning `202`, the service **MUST** record the accepted mode and applicable byte/entry ceilings. If `required` cannot be honored, the request **MUST** fail with `413 atomic_import_too_large`; it **MUST NOT** silently fall back.
3. `preferred` **MAY** fall back to per-entry application, but the status resource **MUST** report `accepted_atomic=false` before application begins.
4. Import states **MUST** include `pending`, `staging`, `validated`, `applying`, `cancelling`, `cancelled`, `succeeded`, and `failed`.
5. Cancellation accepted before the first commit **MUST** delete staged artifacts and end in `cancelled`. During per-entry apply, it **MUST** prevent new entry transactions from starting but **MUST NOT** roll back already committed entries; the status resource **MUST** list those outcomes. Cancellation after an atomic commit or completed job **MUST** return `409 already_committed`.

### 2.5 Namespace, visibility, ownership, and ACL policy

1. `allowed_namespaces` **MUST** conform to:
   ```json
   {
     "rules": [{
       "source_owner_type": "user|team",
       "source_owner_id": "uuid",
       "destination_owner_type": "user|team",
       "destination_owner_id": "uuid",
       "maximum_visibility": "private|team|public",
       "allow_releases": true,
       "allow_deletes": false
     }],
     "default": "deny"
   }
   ```
2. Rules **MUST** be evaluated by exact source owner identity; names and slugs **MUST NOT** establish authority. Multiple matching rules use the lowest visibility ceiling and intersection of permissions.
3. Effective visibility **MUST** be the least permissive of source visibility, request ceiling, matching peer-rule ceiling, and destination-owner ceiling, ordered `private < team < public`.
4. Standard bundles and sync protocol version 1 **MUST NOT** export ownership credentials, ACL records, or ACL events. Imported entries receive destination-local ownership and ACLs.
5. ACL synchronization **MAY** exist only under a separately negotiated `administrative-mirror-acl/1` capability with its own schema, mutual authentication, exact principal mappings, and audit trail. A peer lacking that capability **MUST** reject, not ignore, an ACL event.
6. Visibility changes produced remotely are advisory inputs to the preceding ceiling calculation and **MUST NOT** override local policy.

## 3. Incremental synchronization clauses

### 3.1 Event schemas and immutable content

1. Every event **MUST** contain:
   ```json
   {
     "source_sequence": 1043,
     "event_id": "uuid",
     "root_origin": {"instance_id": "uuid", "event_id": "uuid"},
     "via": ["uuid"],
     "operation": "upsert|delete",
     "resource_type": "entry-snapshot|version|release|tag-assignment|tombstone",
     "resource_id": "uuid",
     "entry_id": "uuid",
     "occurred_at": "RFC3339 UTC",
     "payload": {},
     "payload_sha256": "64 lowercase hex"
   }
   ```
2. `payload_sha256` is SHA-256 of RFC 8785 canonical UTF-8 payload bytes. Payloads **MUST** validate against the schema selected by `(protocol_version, resource_type, operation)`.
3. `entry-snapshot` payloads **MUST** contain complete distributable entry metadata and the remote revision. `version` payloads **MUST** contain complete immutable version/file descriptors and either inline bodies or authenticated content references. `release` payloads **MUST** identify an already supplied version. `tag-assignment` payloads **MUST** contain complete tag identity and add/remove action. `tombstone` payloads **MUST** follow Section 3.8.
4. A content reference **MUST** contain immutable URL, SHA-256, size, media type, expiry, and source instance ID. Fetching it requires the same peer credential; redirects are forbidden; the response **MUST** be signed and hash-verified before commit. A URL that expires before successful fetch causes the whole batch to fail and be retried.
5. Unknown required event types or schema versions **MUST** reject the batch with `409 unsupported_sync_capability`.

### 3.2 Signed envelopes

1. Sync JSON responses and push requests **MUST** carry an embedded `signature` object. They are not detached signatures. Binary content responses use detached HTTP signature headers as specified below.
2. Every envelope **MUST** include:
   ```json
   {
     "protocol_version": 1,
     "source_instance_id": "uuid",
     "request_binding": {
       "method": "GET",
       "path_query": "/api/v1/sync/changes?after=1042&limit=500",
       "request_id": "uuid"
     },
     "generated_at": "RFC3339 UTC",
     "expires_at": "RFC3339 UTC",
     "nonce": "base64url",
     "...": "...",
     "signature": {
       "key_id": "base64url",
       "algorithm": "Ed25519",
       "value": "base64url"
     }
   }
   ```
3. Let `U` be the envelope with `signature` removed. Signing bytes are:
   ```text
   "CCAT-SYNC-ENVELOPE-1\n" ||
   SHA-256(RFC8785(U))
   ```
   Ed25519 signs those bytes directly.
4. Verifiers **MUST** check the expected TLS peer, source instance ID, key ID, request binding, body digest, expiry, and signature before processing events.
5. `expires_at-generated_at` **MUST NOT** exceed five minutes. Clock skew greater than 60 seconds is invalid. Consumers **MUST** retain `(source_instance_id, nonce)` until `expires_at+60s` and reject replay.
6. Binary fetch responses **MUST** include `Digest: sha-256=:<base64>:` plus `X-CCAT-Key-ID`, `X-CCAT-Generated-At`, `X-CCAT-Expires-At`, `X-CCAT-Request-ID`, and `X-CCAT-Signature`. The detached signature covers the same domain prefix and RFC 8785 canonical object containing those fields, status, content type, content length, request path/query, and digest.
7. Conformance vectors **MUST** cover property reordering, Unicode, omitted signature, wrong request binding, replay, expired messages, and binary fetches.

### 3.3 Key identity, bootstrap, rotation, and compromise

1. Instances **MUST** store multiple keys in an `instance_signing_keys` relation containing instance ID, key ID, public key, `not_before`, `not_after`, and `revoked_at`.
2. `key_id` is the unpadded base64url encoding of the first 16 bytes of `SHA-256(public_key_raw_32_bytes)`.
3. Initial trust **MUST** be established out of band by approving the instance ID, base URL, and full public-key fingerprint. Discovery over an unauthenticated connection **MUST NOT** establish trust.
4. Rotation **MUST** be announced by a statement containing instance ID, old/new key IDs, new public key, validity interval, and monotonically increasing rotation sequence. It **MUST** be signed by both the old and new keys and accepted before the old key expires.
5. A normal overlap window **MUST NOT** exceed seven days. Messages signed by revoked, not-yet-valid, or expired keys **MUST** fail.
6. If the old key is compromised or unavailable, replacement requires explicit peer-administrator re-trust. A new key learned solely from a message signed by the compromised key **MUST NOT** clear a recorded revocation.

### 3.4 Durable inbox, quarantine, and cursors

Consumers **MUST** persist a `sync_inbox` row before acknowledging receipt: `(peer_id, source_instance_id, source_sequence, event_id, root_origin, entry_id, envelope_digest, payload, state, attempt_count, next_attempt_at, error_code, error_detail_redacted, received_at, applied_at, quarantined_at)`, where `root_origin` is the structured pair `{instance_id,event_id}`. `state` is `pending|applying|applied|duplicate|quarantined|dead_letter`; unique keys are `(peer_id,source_sequence)`, `(source_instance_id,event_id)`, and `(root_origin.instance_id,root_origin.event_id)`.

1. Pull pages are globally ordered by `source_sequence`. The producer **MUST** scan sequences greater than `after` and set `next_cursor` to the greatest scanned sequence, including events omitted by authorization filters.
2. Signature/schema validation and insertion of the complete page into `sync_inbox`, plus `sync_peers.last_received_cursor=next_cursor`, occur in one transaction. A malformed envelope/page rolls back this transaction. Pull resumes after `last_received_cursor`; therefore advancing the receive cursor cannot lose an unapplied event.
3. `last_contiguous_applied_cursor` is separate: it is the greatest source sequence for which every lower visible inbox row is `applied` or `duplicate`. It stops before a quarantined/dead-letter event and is used for health, reconciliation, and retention acknowledgements; it is never falsely reported as an application cursor.
4. Workers select pending events by entry. Events for one entry apply strictly by source sequence and a quarantined event blocks later events for that entry. Other entries apply independently and may complete even when the contiguous applied cursor is stopped. Each event application and its state transition commit atomically with destination rows/change events.
5. Transient errors retry with exponential full jitter at 1s, 2s, 4s… capped at 60s and five automatic attempts. A deterministic conflict or exhausted retry becomes `quarantined`; after 30 days unresolved it becomes `dead_letter` but is never deleted automatically. Status exposes counts and oldest age without payload leakage.
6. Resolution is an audited peer-admin operation: `retry` returns an event to pending after correcting policy/data; `map` records an explicit principal/namespace resolution then retries; `supersede-by-snapshot` may mark it resolved only after an authoritative signed snapshot covering that entry commits; `discard` is permitted only with two-admin approval, a reason, and forced snapshot reconciliation. Resolution unblocks later same-entry rows and recomputes the contiguous cursor.
7. A push request uses `source_sequence`, never the destination sequence. Envelope validation and inbox insertion are atomic, but application outcomes are per entry. The response contains `source_first_sequence`, `source_last_sequence`, `destination_received_cursor`, and one result per source event: `{event_id,state:"queued|duplicate|quarantined",destination_sequence:null|integer,error_code:null|string}`. `destination_sequence` is assigned only when an applied event creates a local change event; clients obtain later outcomes from `GET /sync/pushes/{push_id}`.
8. If any event is syntactically invalid or the envelope signature fails, no inbox row is committed and the request is non-2xx. Semantic entry conflicts may be quarantined without preventing valid independent entries from processing. Duplicate push replays the original push resource and event results.
9. Peer retention acknowledgement uses `last_contiguous_applied_cursor`, not `last_received_cursor`; a long quarantine eventually triggers the snapshot-required lag policy in Section 3.7.

### 3.5 Filtering and later authorization

1. Cursor advancement across hidden events **MUST NOT** imply that hidden content was delivered.
2. Whenever content changes from excluded to included for a peer, the producer **MUST** emit a new `entry-snapshot` event containing the current distributable state, regardless of whether the underlying content revision changed.
3. Revocation of peer visibility **MUST** emit a scoped tombstone only when the peer policy authorizes deletion propagation; otherwise the peer retains its previously imported local copy under local policy.
4. Search, facet, and status APIs **MUST NOT** reveal hidden event types, IDs, payload sizes, or resource identities.

### 3.6 Relay and loop prevention

1. `root_origin` is immutable across relays. `via` is an ordered array of forwarding instance IDs.
2. A forwarder **MUST** append its own ID, **MUST NOT** forward to the immediate source, and **MUST** reject an event if its own or the destination instance ID already appears in `via`.
3. `via` is limited to 16 IDs. Reaching the limit causes `409 sync_hop_limit`; the list **MUST NOT** be truncated.
4. A relayed event **MUST NOT** acquire a new root event ID, although each producer may assign a local destination sequence.

### 3.7 Retention, lagging peers, and recovery

1. Events are retained for at least 90 days. An enabled peer may delay compaction for at most 30 additional days beyond that floor.
2. A peer that remains behind the proposed compaction watermark for 30 days **MUST** be marked `snapshot_required`; it no longer blocks compaction. Re-enabling incremental sync requires applying a fresh snapshot.
3. Operator override **MUST** be audited and **MUST** set affected peers to `snapshot_required`.
4. `/sync/status` **MUST** expose `current_cursor`, `minimum_cursor`, `retention_time`, and whether a snapshot is required, without exposing unauthorized event contents.

### 3.8 Tombstones and snapshots

1. A tombstone **MUST** contain source instance ID, origin entry ID, tombstone ID, resource type, last known revision/hash, deletion time, and retention deadline. Release tombstones additionally contain entry ID, release name, and former version ID and are retained permanently.
2. Every snapshot **MUST** contain:
   - `snapshot_cursor`;
   - the exact namespace/visibility policy and its SHA-256 digest;
   - all authorized current entries and immutable referenced versions/releases;
   - all unexpired entry and release tombstones applicable to that scope;
   - `authoritative` and `deletion_semantics` fields.
3. Absence from a snapshot **MUST NOT** mean deletion unless `authoritative=true`, the entry falls within the signed scope, and `deletion_semantics="absence-is-deletion"`.
4. Authorization filtering **MUST NOT** be represented as deletion. Non-authoritative snapshots reconcile only explicit objects and tombstones.
5. A consumer **MUST** commit snapshot state and `snapshot_cursor` atomically, then request changes strictly after that cursor.

### 3.9 Network behavior

1. Sync clients **MUST** use a 5-second connect timeout, 30-second read-idle timeout, 120-second whole-request timeout, and maximum page size of 500 events or 16 MiB canonical JSON, whichever is reached first.
2. Clients retry connection failures, `408`, `425`, `429`, `500`, `502`, `503`, and `504`. Other 4xx responses are non-retryable except after explicit credential/key refresh.
3. Retries use exponential backoff starting at one second, multiplier two, full jitter, and a 60-second cap. `Retry-After` takes precedence when longer.
4. After five consecutive failures, a peer enters an open circuit for 60 seconds; repeated openings **MUST** alert an operator. Retries **MUST** preserve the same idempotency key and request body.
5. Poison events cannot be silently skipped. They remain durably quarantined, stop the contiguous applied cursor and later events for the same entry, but do not block application of independent entries or advancement of the receive cursor. Recovery follows Section 3.4 and requires producer correction, retry, authoritative snapshot supersession, or audited operator resolution.

## 4. CTL1 clauses

### 4.1 Grammar and evaluation

The repository **MUST** publish a normative grammar equivalent to:

```ebnf
template      = { text | interpolation | comment | block };
open          = "{{", [ "~" ];
close         = [ "~" ], "}}";
interpolation = open, ws, reference, { ws, "|", ws, transform }, ws, close;
reference     = identifier | "this" | "@index" | "@first" | "@last";
transform     = "trim" | "lower" | "upper" | "snake_case" | "kebab_case"
              | "pascal_case" | "camel_case" | "kebab_to_snake";
comment       = "{{", [ "~" ], "!", { any-except-close }, close;
block         = if-block | unless-block | each-block;
if-block      = "{{", [ "~" ], "#if", ws1, condition, ws, close,
                template, [ open, ws, "else", ws, close, template ],
                "{{", [ "~" ], "/if", ws, close;
unless-block  = "{{", [ "~" ], "#unless", ws1, condition, ws, close,
                template, [ open, ws, "else", ws, close, template ],
                "{{", [ "~" ], "/unless", ws, close;
each-block    = "{{", [ "~" ], "#each", ws1, identifier, ws, close,
                template, [ open, ws, "else", ws, close, template ],
                "{{", [ "~" ], "/each", ws, close;
condition     = unary;
unary         = [ "not", ws1 ], primary;
primary       = boolean-reference
              | reference, ws, ("==" | "!="), ws, literal
              | "contains", ws, "(", ws, identifier, ws, ",", ws, literal, ws, ")"
              | "(", ws, condition, ws, ")";
literal       = json-string | json-number | "true" | "false" | "null";
identifier    = letter, { letter | digit | "_" };
ws            = { " " | "\t" | "\r" | "\n" };
ws1           = (" " | "\t" | "\r" | "\n"), ws;
```

Additional rules:

1. JSON strings and numbers use RFC 8259 lexical forms. No `and`, `or`, coercion, property access, or implicit truthiness exists.
2. A bare condition is valid only for a boolean variable. `contains` requires a homogeneous scalar array and same-typed literal. Equality requires equal types; `null` compares only to an omitted nullable value. Type mismatch is a validation error, not false.
3. Unknown variables/transforms, array interpolation outside `each`, and `this`/`@...` outside `each` are publish-time errors.
4. String interpolation emits the string unchanged. Booleans emit `true` or `false`; integers emit base-10 without leading zero; numbers use RFC 8785 number serialization. Arrays cannot be interpolated directly.
5. Substitution is exactly one pass. Emitted variable text **MUST NOT** be reparsed as CTL, including text containing `{{`, block markers, or trim markers.
6. Literal `{{` and `}}` are encoded as `{{{{` and `}}}}`; delimiter escaping is performed during lexical analysis and escaped delimiters cannot begin directives.
7. Block nesting is limited to 16 and parse failure rejects the version.

### 4.2 Defaults and normalized inputs

1. `variables` in schema version 1 **MUST** be an ordered array of declarations, or implementations **MUST** ignore JSON object order and resolve `default_from`/computed values using a dependency graph.
2. Cycles and references to absent declarations are publish-time errors. Among simultaneously ready graph nodes, evaluation order is ascending UTF-8 variable name bytes.
3. Render inputs **MUST** have exact declared JSON types; coercion is forbidden. Unknown input properties are rejected.
4. Strings are NFC-normalized before constraint checks. Numbers outside the finite interoperable JSON range are rejected; NaN, infinities, and negative zero are forbidden.
5. Array uniqueness is determined by RFC 8785 canonical item bytes.
6. The normalized variable object contains every supplied or defaulted variable and excludes computed variables. Its property names are sorted only by RFC 8785 during hashing.

### 4.3 Transform algorithms

1. `trim` removes only ASCII space, tab, CR, and LF from both ends.
2. `lower`/`upper` map ASCII `A–Z`/`a–z` only; non-ASCII scalars are unchanged.
3. Word-oriented transforms first split on ASCII whitespace and punctuation, `_`, and `-`; split before an uppercase ASCII letter preceded by lowercase ASCII or followed by lowercase ASCII; split between ASCII letters and digits. Empty words are discarded.
4. `snake_case` joins lowercased words with `_`; `kebab_case` joins them with `-`; `pascal_case` uppercases the first ASCII lowercase letter of each lowercased word and concatenates; `camel_case` lowercases the first Pascal word’s initial ASCII letter; `kebab_to_snake` replaces ASCII `-` with `_` without other splitting.
5. Non-ASCII scalars remain in their original word and are never transliterated. Golden vectors **MUST** cover acronyms, digits, punctuation, combining characters, and non-ASCII text.

### 4.4 Whitespace and contextual safety

1. Without trim markers, every non-directive input scalar, including whitespace, is emitted unchanged.
2. A left trim marker `{{~` removes the maximal contiguous run of ASCII space, tab, CR, and LF immediately preceding the directive. A right trim marker `~}}` removes the maximal such run immediately following it. No other whitespace is removed.
3. CTL provides no HTML, shell, SQL, YAML, or language-specific escaping. Render responses and UI **MUST** state that generated source is unescaped and may be unsafe when variables are used in execution-sensitive contexts.
4. The renderer guarantees only non-execution, deterministic substitution, path confinement, and configured resource limits.

### 4.5 Output paths and limits

1. Render requests **MUST** include `target_platform` as `portable`, `linux`, `macos`, or `windows`; default is `portable`.
2. `portable` applies all platform restrictions. Windows device names, trailing spaces/dots, colons, and case-insensitive collisions are rejected. macOS comparison uses NFC and case folding. Linux still rejects collisions under portable comparison when `portable` is selected.
3. Path interpolation follows the same one-pass scalar rules and permits only string/integer variables and transforms.
4. Effective limits are the minimum of service ceilings and schema limits. Service ceilings are immutable for a render job and **MUST** include output files, per-file bytes, total pre-conversion bytes, total post-line-ending bytes, path bytes, path segments, nesting depth, and render CPU/wall time.
5. Crossing any effective limit aborts the whole render; partial output **MUST NOT** be returned or cached.

### 4.6 Secrets and caching

1. CTL1 protocol version 1 **MUST require** `secret_variables` to be empty. Any non-empty declaration or secret-bearing render request is rejected with `422 secret_variables_unsupported`.
2. Render hashes, idempotency records, jobs, metrics, logs, traces, caches, and artifacts therefore **MUST NOT** contain secret-variable values.
3. Introducing secret variables requires a new negotiated CTL capability defining consent, trusted-scaffold provenance, keyed non-public cache derivation, redaction, expiry, and artifact handling; it cannot be a deployment-local extension to CTL1.

### 4.7 Line endings and deterministic render ZIP

1. Before CTL parsing, every template text file converts CRLF and lone CR in the stored source to LF. Supplied and defaulted string variables likewise convert CRLF and lone CR to LF after NFC normalization and before validation/hash; therefore substitutions cannot introduce unnormalized line endings.
2. Rendering and all pre-conversion byte ceilings are measured on the resulting UTF-8 LF bytes. The requested `line_endings` conversion is a final single pass over every text output file: `lf` leaves LF unchanged and `crlf` replaces each LF with CRLF. Non-template text files follow the same source-normalization and final conversion; binary files are copied byte-for-byte and never converted. Post-conversion files and aggregate output are checked again against effective limits.
3. CTL ZIP output **MUST** use the canonical ZIP profile in Section 2.2, except timestamps are taken from the immutable scaffold version. The render manifest **MUST** include renderer version, target platform, line-ending mode, normalized non-secret variables, and every output hash. Byte-for-byte golden archives are required for every supported renderer.

## 5. Search clauses

### 5.1 Normalization and query construction

1. Title normalization is the application algorithm: Unicode NFKD using Unicode 15.1, removal of characters in General Category `Mn`, Unicode default case folding using Unicode 15.1 tables, then NFC. Implementations **MUST NOT** depend on deployment-local `unaccent.rules`.
2. For non-empty `q`, construct:
   ```sql
   q_en = websearch_to_tsquery('english', q)
   q_simple = websearch_to_tsquery('simple', q)
   ```
   An entry matches FTS when `document @@ q_en OR document @@ q_simple`.
3. The same web-search operators, quoting, negation, and prefix syntax are passed identically to both PostgreSQL configurations. Parser errors return `422 invalid_query`.
4. After Unicode whitespace trimming, an empty query behaves as no `q`. If both queries contain no positive lexemes, return an empty result with no trigram fallback.

### 5.2 Exact ranking and candidate union

For each authorized matching entry:

```text
english_rank = ts_rank_cd(weights, document, q_en, 32)
simple_rank  = ts_rank_cd(weights, document, q_simple, 32)
text_rank    = min(1.0, 0.70*english_rank + 0.30*simple_rank)
exact_title  = 1 if title_normalized == normalized_q else 0
title_prefix = 1 if title_normalized begins normalized_q else 0
age_days     = clamp((ranking_time-updated_at)/86400, 0, 180)
freshness    = 1 - age_days/180
score        = text_rank + 0.50*exact_title + 0.15*title_prefix
               + 0.05*freshness
```

1. Compute all rank components as PostgreSQL `float8`, clamp as written, then round the final `score` to 12 decimal places using round-half-away-from-zero before ordering or cursor serialization. Results order by `score DESC, updated_at DESC, entry_id ASC`; the cursor carries the decimal score string, not a binary float.
2. If fewer than ten authorized FTS candidates exist and normalized query length is at least three scalars, add authorized entries whose normalized-title trigram similarity is at least `0.30`.
3. A trigram-only candidate uses `text_rank=0` and adds `0.20*similarity` to the formula. An entry matching both pipelines appears once with the higher computed score.
4. The union and rank formula apply to every page, not only page one.

### 5.3 Relevance pagination

1. The first page fixes `ranking_time` to the database transaction timestamp and includes it, the normalized query hash, filters hash, last score, last updated time, last entry ID, and expiry in the signed cursor.
2. Subsequent pages reuse that `ranking_time` and keyset predicate. An entry already returned **MUST NOT** be returned again.
3. Entries created or newly made visible after `ranking_time` are excluded. An entry updated after `ranking_time` may be omitted from later pages; this is the only permitted page drift and **MUST** be documented.
4. Cursor TTL defaults to 15 minutes. Expired cursors return `410 cursor_expired`; filter, authorization-subject, or sort mismatch returns `400 invalid_cursor`.
5. Deployments requiring zero omissions **MAY** materialize ordered result IDs for the cursor TTL, but must preserve the same score and authorization rules.

### 5.4 Facets

1. `GET /entries` **MUST** accept repeated `facet=tag|language|kind|category` and return:
   ```json
   {
     "facets": {
       "tag": {
         "approximate": false,
         "counts": [{"value": "uuid-or-slug", "count": 12}]
       }
     }
   }
   ```
2. Facets are computed over the authorized, fully filtered result set before pagination, excluding the facet’s own filter only when `facet_mode=disjunctive` is explicitly requested.
3. Anonymous facet counts below five **MUST** be suppressed or grouped into `other`; private/team entries **MUST NOT** contribute to anonymous counts.
4. Approximation is permitted only above a configured cost threshold. Responses **MUST** identify approximation and its documented relative-error bound; approximation must not bypass authorization predicates.

### 5.5 SQL and synchronous maintenance

1. All search text, tags, languages, category prefixes, owner IDs, arrays, and cursor values **MUST** be bound SQL parameters. Sort expressions and operators **MUST** come from fixed allowlists. User text **MUST NOT** be interpolated into `tsquery`, SQL fragments, regexes, or materialized paths.
2. Repeated filter arrays are limited to 50 values and each value to 128 UTF-8 bytes.
3. Updating `entry_search` is part of the content/metadata transaction. It has a two-second statement timeout by default; timeout or index-maintenance failure rolls back the catalogue mutation and returns `503 search_index_update_failed`.
4. The implementation **MUST** benchmark write amplification and GIN bloat before production enablement. It **MUST** alert on search-row transaction p95 above 500 ms or GIN pending-list growth beyond configured limits.

### 5.6 Reproducible SLO test

The search SLO is conformant only when measured with a published fixture or generator specifying:

- 1,000,000 entries and 10,000,000 files;
- title/tag/language/category frequency distributions;
- current-version text-size distribution up to the indexing ceilings;
- at least 10% private and 20% team-visible entries;
- authenticated subjects with 1, 10, 100, and 1,000 team memberships;
- query mix covering exact title, common terms, rare terms, code identifiers, stop words, filters, facets, and no-result queries;
- PostgreSQL/hardware/storage configuration;
- 50 concurrent clients after a ten-minute warm-up;
- both warm-cache and database-restart cold-cache runs;
- at least 10,000 measured requests over a rolling five-minute window.

The stated p95 target **MUST** be met separately for the authenticated membership cohorts and anonymous queries; averaging cohorts is not permitted.

## 6. Security clauses

### 6.1 API-token verification and non-escalation

1. API token secrets contain at least 256 random bits. The database stores:
   ```text
   verifier = HMAC-SHA-256(
     K_token_verifier,
     token_id_raw || secret_raw
   )
   ```
   where `K_token_verifier` is held in KMS/secret storage and never in the database.
2. Verification performs indexed token-ID lookup, recomputes the HMAC, and compares all 32 bytes in constant time. Argon2id **MUST NOT** be performed on every authenticated request.
3. Verifier-key rotation **MUST** support overlapping key IDs and opportunistic migration. Loss of the verifier key revokes affected tokens; plaintext tokens cannot be reconstructed.
4. Token creation **MUST** enforce that requested scopes are a subset of the creator credential’s scopes and current authority. Team restrictions must be a subset of teams the creator may delegate. Service ownership/ACL grants require explicit owner authority. `admin:*` requires a site administrator using an interactive, MFA-authenticated session.
5. Rotation overlap has an explicit expiry no longer than ten minutes. Revocation and expiry checks **MUST** consult authoritative state for sensitive writes and sync operations; invalidation **MUST** reach all nodes within five seconds.

### 6.2 Pre-authentication and anonymous limits

Before expensive token hashing, OIDC processing, search, rendering, URL fetch, or signature verification, the service **MUST** enforce token-bucket limits. Defaults:

| Operation | Per source IP | Global |
|---|---:|---:|
| invalid/unknown token ID | 20/min | 2,000/min |
| token verification failures | 10/min | 1,000/min |
| OIDC initiation/callback failure | 10/min | 1,000/min |
| anonymous search | 60/min | 10,000/min |
| anonymous export | 5/hour | 500/hour |
| anonymous render, if enabled | 2/min and 10/hour | 100/min |
| source-URL imports | 5/hour | 200/hour |
| sync signature failures | 10/min per peer/IP | 500/min |

1. Limits **MUST** also include bounded network-prefix and deployment-wide concurrency controls.
2. Rejection returns `429` with `Retry-After` and performs no expensive verifier, archive, render, or query work.
3. Unknown token IDs and wrong secrets **MUST** return indistinguishable errors and comparable bounded response times.

### 6.3 Download and response security

1. User-derived filenames **MUST** have CR, LF, NUL, `/`, and `\` removed from the fallback name.
2. `Content-Disposition` **MUST** use a conservative ASCII `filename` plus RFC 5987 `filename*=UTF-8''...`; values **MUST** be generated by a library, never string interpolation.
3. Private/raw/export responses **MUST** include:
   ```text
   Cache-Control: private, no-store
   Vary: Authorization, Cookie
   X-Content-Type-Options: nosniff
   Referrer-Policy: no-referrer
   ```
4. Public immutable version bodies may use `public, max-age=300, must-revalidate` only when URLs contain immutable version IDs and no credential material.
5. Signed object/download URLs **MUST** expire within 15 minutes, be bound to object identity and disposition, and not confer access to another object.
6. Public-to-private, unpublish, archive, and delete transitions **MUST** synchronously revoke future signed URLs and enqueue CDN/object-cache purge before returning success. Until purge acknowledgement, origin authorization **MUST** deny the object. Purge failure **MUST** alert operators.

### 6.4 SSRF and outbound requests

1. Remote imports and sync fetches use HTTPS only, except explicitly configured peer endpoints.
2. The client **MUST** resolve DNS before each connection and after every redirect; all resolved addresses must be checked against denied loopback, private, link-local, multicast, carrier-grade NAT, and cloud metadata ranges.
3. Hostname, scheme, and port changes across redirects are denied unless explicitly allowlisted. Credentials and authorization headers **MUST NOT** be forwarded across origins.
4. The client applies the size, redirect, timeout, and concurrency ceilings above while streaming; `Content-Length` does not replace streamed byte accounting.

### 6.5 Generated-content safety

1. Because CTL1 secret variables are forbidden, unattended injection of credentials into rendered artifacts is also forbidden.
2. Render responses **MUST** identify the source entry, immutable version, origin instance, owner, and whether the scaffold is locally trusted.
3. Generated code **MUST** be served as download/text content and never executed or previewed in the application origin. Any future preview requires an isolated origin with no ambient credentials and a restrictive CSP.

### 6.6 Acceptance tests

Conformance tests **MUST** include:

- signature canonicalization, replay, key overlap, revocation, and emergency re-trust;
- hidden-event cursor advancement and later visibility snapshots;
- durable inbox receipt, per-entry quarantine with independent progress, duplicate push, crash before/after receive/application cursor commits, snapshot tombstones, and relay hop loops;
- malformed ZIP names, duplicate/case/Unicode collisions, unsupported members, every archive ceiling, and cancellation races;
- CTL injection through variable values, malformed literals, type mismatch, trim boundaries, transform edge cases, path collisions, and exact ZIP bytes;
- mixed English/simple ranking, stop-word-only queries, trigram pagination, authorization changes between pages, facet suppression, and all team-membership benchmark cohorts;
- invalid token-ID floods, verifier-key rotation, token delegation escalation, filename/header injection, stale signed URLs, CDN purge failure, and SSRF DNS rebinding.
